### Implementation Details

1. **TTL Parsing and Precedence Representation**:
   - Define supported Anthropic cache TTL ranks: `"1h": 3600` (longer TTL) and `"5m": 300` (default ephemeral TTL when `ttl` is omitted or explicitly `"5m"`).
   - Implement `_parse_ttl_rank(cc: Any) -> int`:
     - Returns `3600` if `isinstance(cc, dict)` and `cc.get("ttl") == "1h"`.
     - Returns `300` for valid default `"ephemeral"` blocks (`ttl` omitted or `"5m"`).
   - Implement `_sanitize_cache_control_block(block: dict[str, Any]) -> bool`:
     - Validates `cc = block.get("cache_control")`.
     - If `cc` is `None` or not a `dict` or `cc.get("type") != "ephemeral"`, removes `"cache_control"` from `block` and returns `False`.
     - If `"ttl"` is present in `cc`:
       - If `cc["ttl"]` is not in `("5m", "1h")` (e.g., `None`, empty string, integer, or unsupported duration string), strips the invalid `"ttl"` key so the block defaults cleanly to standard ephemeral (`5m`).
     - Returns `True` when a valid `cache_control` dictionary remains attached.

2. **Ordered Cache Control Breakpoint Traversal Across `tools -> system -> messages`**:
   - Note Anthropic's prefix hierarchy evaluation order (`tools`, then `system`, then `messages`) as well as sequential block order within each section (`system.0`, `system.1`, `system.2`, ...). To guarantee non-increasing TTL order regardless of whether Anthropic validates `tools -> system -> messages` or `system -> tools -> messages`, ensure that:
     - Within `tools`, `system`, and `messages`, and across the full request breakpoint sequence, no breakpoint has a longer TTL than any preceding breakpoint, AND when both `tools` and `system` carry breakpoints, their TTLs are harmonized or ordered so neither order violates `longer TTL >= shorter TTL`.
     - Specifically, implement `_iter_cache_control_holders(payload: dict[str, Any]) -> Iterator[tuple[str, dict[str, Any]]]`:
       - Yields `(section, block_dict)` for every block in `tools`, `system`, and `messages` (including top-level message dicts and nested message `content` blocks) that contains `"cache_control"`.
     - Even better: check both `(tools, system, messages)` and `(system, tools, messages)` or normalize TTLs across existing and injected breakpoints so that:
       1. Every `cache_control` block in `payload` is sanitized via `_sanitize_cache_control_block`.
       2. If total existing `cache_control` blocks exceed the 4-breakpoint maximum (`MAX_CACHE_BREAKPOINTS = 4`), excess `cache_control` markers beyond the first 4 (or lowest-priority duplicates) are stripped so the payload never exceeds 4 breakpoints.
       3. Non-increasing TTL order is enforced across the sequence: as we traverse breakpoints in evaluation order, track `max_allowed_rank` (initialized to `3600`). When a breakpoint has `rank < max_allowed_rank` (i.e. `300` for `5m`), `max_allowed_rank` drops to `300`. Any subsequent breakpoint with `rank > max_allowed_rank` (e.g. a `"1h"` TTL appearing after an implicit or explicit `"5m"` TTL, such as `system.0` having `{"type": "ephemeral"}` and `system.2` having `{"type": "ephemeral", "ttl": "1h"}`) has its `"ttl"` downgraded (removing `"ttl": "1h"` or setting it consistent with `max_allowed_rank`) so it never triggers HTTP 400 `cache_control.ttl: Extra inputs are not permitted` / TTL ordering errors.
       4. If `tools` has a `5m` breakpoint and `system` has a `1h` breakpoint (or vice versa), downgrade the later section's `1h` or upgrade/align so both `tools -> system -> messages` and `system -> tools -> messages` see non-increasing TTLs (`tools_rank >= system_rank >= messages_rank` when `tools` precedes `system`, and if `system` has `1h` while `tools` has `5m` without explicit `ttl`, either match `tools` to `1h` when injecting or downgrade conflicting `1h` after `5m`).

3. **TTL-Compatible Injection in `inject_anthropic_cache_control`**:
   - Before counting and injecting, run `sanitize_and_normalize_cache_controls(payload)` so invalid `cache_control` blocks are cleaned, breakpoint count is capped at $\le 4$, and existing multi-block TTL sequences (like `system.0` (`5m`) followed by `system.2` (`1h`)) are normalized to valid non-increasing TTL order even when `budget <= 0` or no new breakpoints are injected.
   - When `enable_prompt_caching` is False, `AnthropicProvider.clean()` still calls `sanitize_and_normalize_cache_controls(payload)` so pre-existing client payloads with malformed or misordered `cache_control.ttl` blocks are repaired before forwarding.
   - During `_inject_system_cache`, `_inject_tools_cache`, and `_inject_messages_cache`:
     - Determine the required TTL for each injection position so it never violates TTL ordering relative to breakpoints that appear after it!
     - Specifically: if any existing breakpoint in `system` or `messages` (or later in the same section) uses `"ttl": "1h"`, injecting a bare `{"type": "ephemeral"}` (which defaults to `5m`) _before_ that `"1h"` block would cause the subsequent `"1h"` block to fail with HTTP 400 (`system.2.cache_control.ttl`).
     - Therefore, `_build_injected_cache_control(required_min_rank: int) -> dict[str, Any]` attaches `{"type": "ephemeral", "ttl": "1h"}` if any downstream breakpoint in the payload has `"ttl": "1h"` (and no upstream breakpoint has already dropped the ceiling to `5m`), or `{"type": "ephemeral"}` otherwise; followed by a final pass of `sanitize_and_normalize_cache_controls(payload)` to guarantee the invariant: $\le 4$ breakpoints and strictly non-increasing TTL ranks across both `system -> tools -> messages` and `tools -> system -> messages`.
